PROBLEM / 问题定义

语音输入不只是“能转写”。

在邮件、即时通讯、文档和 AI 编程等桌面场景中，用户真正需要的是可直接提交的文本。现有方案仍要求用户记忆快捷键、确认录音状态、手动整理口语并处理跨应用输入，操作链路被切成多个断点。

PressTalk 的产品假设是：实体 PTT 按键和旋钮可以降低启动与模式切换成本；上下文 LLM 则负责把自然口语整理成符合当前应用和选中文本语境的表达。

SOLUTION / 产品方案

把输入体验做成一条闭环。

从物理触发到文本落地，每一步都有明确输入、状态和失败回退。

01

按住说话

实体按键或快捷键触发录音，明确开始与结束。

02

ASR 转写

本地完成语音识别，保留自定义词典和术语纠正。

03

上下文整理

结合当前应用与选中文本完成去口语化、翻译或改写。

04

跨应用注入

将可直接使用的文本写入当前 Windows 应用。

EXPERIMENTS / 关键取舍

用 POC 数据收敛路线。

重点不是证明所有方案都能做，而是尽早判断哪条路线值得进入默认产品。

01

本地 AI 是否适合作为默认方案？

假设

本地处理可以提升隐私感知，并减少云端模型调用。

证据

完成 30 项测试；CPU 环境下短文本润色约 7.1 秒，运行内存不低于 16 GB。

决策

不把全本地方案作为默认路径，采用本地 ASR + 云端 LLM 的混合架构。

查看本地化 POC
02

纯 BLE 能否承载实时音频？

假设

BLE 可以减少连接步骤，让设备以单一无线链路工作。

证据

16 kHz / 16-bit 单声道 PCM 需要约 32 KB/s 持续带宽，实测出现队列积压与链路余量不足。

决策

USB / Wi-Fi 作为音频主链路，BLE 聚焦辅助配网和轻量控制。

查看 BLE Demo
03

如何兼顾体验与模型成本？

假设

ASR 留在本地、文本整理放在云端，可以保留体验并控制成本。

证据

当前 POC 测试中，60 秒语音处理成本约为全云端方案的 10%，转写准确率超过 97%。

决策

将混合架构作为当前主方案，并把质量、延迟与成本纳入后续 Beta 指标。
